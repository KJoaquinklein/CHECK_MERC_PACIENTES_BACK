# Decisiones de diseño

Registro de las decisiones tomadas ante ambigüedades del plan (qué se decidió y por qué).

## Generales

- **Sin ORM.** Se mantiene `pg` con SQL parametrizado a mano, como indica el plan: el esquema usa columnas generadas, triggers, `unaccent`/trigramas y `SELECT ... FOR UPDATE`, que un ORM maneja mal.
- **Sin Docker.** No hay Docker en la máquina de desarrollo. PostgreSQL de desarrollo y tests se aloja en Render, en una **base separada de la de producción** (los tests borran y recrean datos). Los tests de integración deben negarse a correr si `DATABASE_URL` no apunta a una base de pruebas. El plan pedía probar S3 contra MinIO en docker (fase 5): se resolverá con un bucket de pruebas real o se documentará la alternativa.
- **Node.** El plan pide Node 22 LTS; la máquina tiene Node 24. `engines` exige `>=22` y `@types/node` está fijado en 22 para no usar APIs que no existan en 22.
- **Commits.** Solo se hacen cuando el desarrollador lo pide.

## Fase 0

- **`/salud` es solo de vida (liveness).** No consulta la base: si la base tiene un corte breve, el hosting no debe reiniciar el contenedor. Se evaluará un chequeo de base aparte si hace falta.
- **413 para bodies mayores al límite JSON** (`PAYLOAD_DEMASIADO_GRANDE`). El plan no lista ese código; es el estándar HTTP y evita responder 500.
- **`X-Request-Id` siempre generado por el servidor.** Se ignora el que mande el cliente, para evitar inyección en los logs.
- **Logs sin query string.** Solo se registra la ruta, porque filtros como `q` pueden contener nombres o DNI.
- **Rate limit general:** 300 peticiones por minuto por IP (`RATE_LIMIT_MAX`). El límite estricto de `/auth/login` se agrega en la fase 2.
- **Variables S3 obligatorias solo con `STORAGE_DRIVER=s3`**, y el driver `local` se rechaza en producción.
- **Los errores de entorno nunca muestran valores**, solo el nombre de la variable (la `DATABASE_URL` lleva contraseña).
- **`npm audit`:** 0 vulnerabilidades en dependencias de producción. Hay avisos de severidad moderada solo en herramientas de desarrollo; ninguna alta ni crítica.

## Fase 1

- **Migración 001** es el SQL del plan tal cual, sin el `BEGIN`/`COMMIT` (node-pg-migrate ya envuelve cada migración en una transacción) y con una sección "Down" que solo sirve en desarrollo y tests.
- **Roles (5.2) se crean con un script, no con una migración**: `npm run crear-roles` (idempotente) toma las contraseñas de variables de entorno, porque un archivo de migración versionado no debe contener contraseñas. Además deja a `hc_migrator` con permiso de crear en el esquema, y quita `CREATE` a `PUBLIC` para que la app nunca pueda crear objetos. La migración 002 solo contiene los permisos y falla con un mensaje claro si el rol `hc_app` no existe.
- **`pgmigrations` es invisible para `hc_app`** (el `GRANT ... ON ALL TABLES` del plan la habría incluido): se revoca en la migración 002.
- **Permisos por defecto** (`ALTER DEFAULT PRIVILEGES`): las tablas futuras quedan con SELECT/INSERT/UPDATE para `hc_app` y sin DELETE. Si una tabla nueva es de solo inserción hay que revocar UPDATE en su propia migración.
- **Dos conexiones distintas:** `DATABASE_URL` (hc_app) para la API y `MIGRATIONS_DATABASE_URL` (hc_migrator) solo para migrar. Las migraciones corren por `npm run migrar`, nunca al arrancar la API. Revertir (`down`) se bloquea con `NODE_ENV=production`.
- **Tipos de `pg`:** `bigint` se devuelve como número (ids y `count(*)`; nunca se acercan a 2^53) y `date` como texto `YYYY-MM-DD`, para que el JSON no cambie el día por la zona horaria.
- **SSL:** `DATABASE_SSL=true` valida el certificado (`rejectUnauthorized: true`). Si algún hosting presenta un certificado no verificable, se decide caso por caso; no se desactiva la validación por defecto.
- **Tests de integración:** usan `TEST_DATABASE_URL` (hc_app) y `TEST_MIGRATIONS_DATABASE_URL` (hc_migrator). Se niegan a correr si el nombre de la base no contiene "test" o "prueba". Sin esas variables se omiten, y el resto de los tests sigue corriendo. Al empezar la corrida se migra desde cero (down + up) y entre tests se vacían las tablas con `TRUNCATE` usando el rol migrador. Los archivos de test no corren en paralelo porque comparten la base.
- **Verificación:** la fase se validó contra un PostgreSQL temporal y descartable (binarios de `embedded-postgres` en una carpeta fuera del proyecto, no es dependencia). Falta repetirla contra la base real de Render.

## Fase 2

- **Respuestas de un solo recurso** (login, `me`, usuarios) devuelven el objeto directamente; solo los listados usan `{ data, meta }`. Un `DELETE` de usuario devuelve el usuario ya desactivado (200). Logout devuelve 204.
- **Nombres de usuario en minúsculas** (3 a 50 caracteres: letras, números, `.`, `-`, `_`). El login tampoco distingue mayúsculas. Así no pueden existir `Doctora` y `doctora` a la vez.
- **Un usuario bloqueado por intentos recibe el mismo 401 genérico** (no un 429 específico), aun con la contraseña correcta: responder distinto revelaría que el usuario existe. El motivo queda en la auditoría (`login_fallido.detalle.motivo`) para que un administrador lo vea. Los intentos durante un bloqueo no lo extienden (evita que un tercero mantenga bloqueada una cuenta ajena para siempre), y al vencer el bloqueo el conteo vuelve a empezar.
- **La auditoría de un login fallido no guarda lo que se escribió** (ni usuario ni contraseña), solo el motivo.
- **Con el cambio de contraseña pendiente** se permiten `POST /auth/cambiar-password` y también `POST /auth/logout` (si no, el usuario quedaría atrapado). `GET /auth/me` responde 403 `DEBE_CAMBIAR_PASSWORD`; ese código le indica al frontend qué pantalla mostrar.
- **Cambiar la contraseña cierra las demás sesiones** del usuario (conserva la actual). Restablecerla (admin) cierra todas.
- **Contraseñas:** mínimo 10 y máximo 128 caracteres (el máximo evita usar argon2 para agotar recursos). argon2id con los parámetros mínimos de OWASP (19 MiB, 2 iteraciones, 1 hilo).
- **Cambiar la contraseña y el login comparten el límite estricto por IP** (`LOGIN_RATE_LIMIT_MAX`, 10 cada 15 minutos por defecto); la contraseña actual podría adivinarse con una cookie robada.
- **Reglas de administradores:** nadie puede cambiar su propio rol ni desactivarse, ni restablecer su propia contraseña por la vía de administrador (`AUTO_MODIFICACION`, 422). Editar su propio nombre sí se permite. `ULTIMO_ADMIN` (422) protege que siempre quede un administrador activo; las filas de los administradores activos se bloquean (`FOR UPDATE`) antes de decidir, así que dos bajas simultáneas no pueden dejar al sistema sin administradores (hay test).
- **Reactivar un usuario** (`PATCH activo=true`) limpia su bloqueo por intentos fallidos.
- **Cookie `sid`:** `Secure` siempre, salvo con `NODE_ENV=test` (los tests usan http). Navegadores como Chrome aceptan `Secure` en `localhost`; si algún navegador de desarrollo no lo hace, se probará por HTTPS.
- **CSRF:** `X-Requested-With` (cualquier valor no vacío) es obligatorio en todo método que no sea GET/HEAD/OPTIONS, incluido el login.
- **Inactividad de la sesión: 120 minutos (el plan decía 60).** Pedido del cliente: las consultas pueden ser largas. Se mantiene el tope absoluto de 12 horas. Escribir en un formulario no genera pedidos al servidor, así que el frontend envía un aviso de actividad liviano (`GET /auth/me`) cada pocos minutos *mientras el usuario mueve el mouse o teclea*; sin actividad no avisa y a los 120 minutos la sesión vence. Aun así, el texto de una consulta en curso no se pierde al vencer la sesión: el frontend la guarda como borrador en el navegador.
- **Sesiones:** al iniciar sesión se borran las sesiones vencidas o revocadas de ese usuario (único DELETE que tiene `hc_app`). Cada petición autenticada renueva `ultimo_uso` en la misma consulta que valida la sesión.
- **`/auditoria`:** en esta fase solo existe el router con la restricción de rol `admin` (para cumplir los 403 pedidos). Los endpoints de consulta son de la fase 6.
- **`npm run crear-admin`** pide usuario, nombre y contraseña (oculta al tipear) por consola y usa `DATABASE_URL`. El administrador creado no queda obligado a cambiar la contraseña, porque la eligió él mismo.
- **`npm audit`:** 3 avisos moderados en `glob`/`minimatch`, dependencias de `node-pg-migrate` (herramienta de migraciones, no corre dentro de la API). Ninguno alto ni crítico. Bajar `node-pg-migrate` a la 7.6 los eliminaría pero es un cambio incompatible: se deja pendiente.
- **Tests:** los tests de integración contra Render tardan unos 3-4 minutos por la latencia de red y el costo de argon2. Para iteraciones rápidas se puede correr un archivo: `npx vitest run tests/auth.test.ts`.

## Fase 3

- **Búsqueda de pacientes por palabras:** el texto `q` se separa en palabras (máximo 10) y todas deben aparecer, en cualquier orden ("angel jose" encuentra a "José Ángel"). El plan describe un único `LIKE` con el texto completo; esto lo amplía sin perder el caso pedido. Cada palabra se escapa (`\`, `%`, `_`) y se pasa por `f_unaccent(lower(...))`. Una palabra hecha solo de dígitos y puntos ("30.123.456") se normaliza a dígitos, que es como se guarda el DNI.
- **Respuesta del listado:** trae datos de identificación y contacto, obra social, `ultima_consulta` y `total_consultas`, pero **no** `domicilio` ni `observaciones` (esas van solo en la ficha). `total_consultas` y `ultima_consulta` ignoran las consultas anuladas. Los pacientes sin consultas van al final al ordenar por `ultima_consulta`, tanto ascendente como descendente.
- **Filtros de fecha de alta** (`creado_desde`, `creado_hasta`, ambos inclusivos) se interpretan como días calendario en hora de Córdoba. Un rango invertido devuelve 400.
- **`/pacientes/conteo`** acepta exactamente los filtros del listado y rechaza `orden`, `dir` y paginación (400).
- **`/pacientes/resumen`:** `total`, `activos`, `inactivos` y `nuevos_*` cuentan a todos los pacientes; `sin_dni`, `sin_obra_social` y `por_obra_social` cuentan **solo pacientes activos**. "Semana" es la semana calendario desde el lunes y "mes" el mes calendario, ambos en hora de Córdoba. `por_obra_social` omite las obras sociales sin pacientes.
- **DNI:** se aceptan puntos, espacios y guiones al escribirlo y se guarda solo con dígitos (6 a 9). Se puede corregir, pero **no borrar** una vez cargado (`dni: null` en un PATCH devuelve 400): es el dato que identifica al paciente. En el alta sí puede omitirse.
- **Pacientes dados de baja no se editan:** `PATCH` responde 409 `PACIENTE_INACTIVO` hasta reactivarlos. Es la lectura más segura del plan, que solo prohíbe consultas y archivos nuevos; si hace falta corregir datos de un inactivo, se reactiva, se edita y se vuelve a dar de baja.
- **Obra social de un paciente:** al asignarla debe existir (`OBRA_SOCIAL_INVALIDA`, 422) y estar activa (`OBRA_SOCIAL_INACTIVA`, 422). Un paciente que ya tenía una obra social que después se dio de baja la conserva.
- **Auditoría de pacientes:** `paciente_crear` guarda solo los **nombres** de los campos cargados. `paciente_editar` guarda antes y después de los datos administrativos (nombre, DNI, fecha de nacimiento, teléfono, email, domicilio, obra social, afiliado), pero de `observaciones` solo deja constancia de que cambió, porque ese campo puede tener texto clínico. Una edición sin cambios reales no audita ni modifica `actualizado_en`. Repetir una baja o una reactivación tampoco genera otro registro.
- **Obras sociales no se auditan:** el plan no incluye acciones de auditoría para el catálogo, así que no se registran. Es un dato compartido y sin información de pacientes.
- **Obras sociales:** el listado es paginado como el resto (máximo 100 por página; el frontend puede pedir `page_size=100&activa=true` para un desplegable). Se puede reactivar con `PATCH { "activa": true }`. El nombre es único sin distinguir mayúsculas (409 `OBRA_SOCIAL_DUPLICADA`), pero sí distingue tildes ("Medifé" y "Medife" son distintas): el índice del plan es sobre `lower(nombre)`.
- **Rutas:** se mantuvieron tal cual el plan (`/pacientes/paciente/:id`, etc.). Las rutas fijas `/conteo` y `/resumen` se declaran primero.
- **Tests:** los archivos que no necesitan usuarios nuevos inician sesión una sola vez y entre tests solo vacían datos clínicos y auditoría (`limpiarDatosClinicos`). La suite completa tarda unos 5 minutos contra Render.

## Fase 4

- **Límite de cuerpo en consultas:** el plan fija un máximo de 100.000 caracteres de contenido y un límite general de 100 KB para el JSON, que no son compatibles (con tildes o emojis 100.000 caracteres pesan hasta ~400 KB). Se mantiene el límite de 100 KB en toda la API **salvo** `/consultas`, que admite hasta 450 KB (más que eso devuelve 413). Para que no se parsee dos veces, el parser global se salta las rutas de consultas.
- **Fecha clínica** (`fecha_consulta`): instante ISO 8601 **con zona horaria** (ej. `2024-05-10T15:30:00-03:00`); una fecha sin zona o solo con día se rechaza porque sería ambigua. No puede ser futura (margen de 5 minutos por diferencias de reloj) ni anterior a 1900: agenda y turnos están fuera de alcance. Si se omite, se usa el momento actual.
- **Pacientes dados de baja:** no pueden recibir consultas nuevas (regla 1 del plan) y, por la misma lectura segura que en la fase 3, tampoco se **editan, cambian de fecha, anulan ni restauran** sus consultas existentes (409 `PACIENTE_INACTIVO`). Leerlas sí está permitido. Para modificar algo se reactiva al paciente. Un paciente inexistente en el cuerpo del alta devuelve 422 `PACIENTE_INVALIDO`.
- **Ediciones:** siguen el orden del plan (bloqueo `FOR UPDATE` de la consulta, comparación de `version_base`, inserción) y devuelven 201 con la consulta ya en su versión nueva. `CONFLICTO_VERSION` (409) incluye en `details` la versión vigente (`[{ "version_vigente": n }]`) para que el frontend pueda avisar. Una edición idéntica a la vigente (comparando sin espacios en los extremos) es 422 `CONTENIDO_SIN_CAMBIOS`. Si la consulta está anulada es 422 `CONSULTA_ANULADA`. Si ocurriera una carrera que el bloqueo no cubra, el `UNIQUE (id_consulta, version)` de la base responde también 409.
- **El contenido se guarda sin espacios en los extremos** (el plan pide `trim`). El `motivo_edicion` es opcional, de hasta 500 caracteres.
- **Cambio de fecha** (`PATCH`): solo acepta `fecha_consulta`, no crea versiones, se audita con el antes y el después (son fechas, no texto clínico), y **marca `fecha_estimada = false`** porque el profesional está fijando una fecha real. Si la nueva fecha es el mismo instante, no cambia ni audita. Una consulta anulada no se puede cambiar de fecha.
- **Anular y restaurar** son idempotentes (repetir la operación no duplica la auditoría) y devuelven la consulta. Las anuladas no aparecen por defecto, no cuentan en `total_consultas` de la ficha del paciente y se pueden leer.
- **Lectura y auditoría:** `GET /consultas/:id` registra `ver_consulta` con la versión vista. El historial completo (`/versiones`) y una versión puntual también registran `ver_consulta` (con `vista: "versiones"` o `"version"`), porque exponen texto clínico de un recurso puntual; el plan solo lista esa acción de lectura. El listado no se audita. `consulta_editar` guarda las versiones anterior y nueva y si hubo motivo, **nunca el texto del motivo ni el contenido**.
- **`/versiones` incluye el contenido de cada versión**, con fecha, usuario (id y nombre) y motivo, en orden ascendente. Una versión inexistente o una consulta inexistente devuelven 404.
- **Búsqueda de texto** (`q`): usa `plainto_tsquery('es_unaccent', q)` sobre la versión vigente solamente, con un `LATERAL` equivalente a la vista `consulta_actual` pero que resuelve una consulta puntual sin recorrer toda la tabla. Todas las palabras deben aparecer (AND) y se ignoran tildes, mayúsculas y variantes de género o número ("dolores" encuentra "dolor"). Un texto de solo palabras vacías ("de la") no coincide con nada.
- **Listado:** orden por `fecha_consulta`, **descendente por defecto** (lo más reciente primero). Cada ítem trae `paciente { id, nombre_completo }`, `version_actual`, `fue_editada` y un extracto de los primeros 200 caracteres de la versión vigente. Las fechas `desde` y `hasta` (inclusivas) son días calendario de Córdoba.
- **Todos los usuarios autenticados** pueden usar estas rutas (el plan no restringe consultas por rol).

## Fase 5

- **La subida pasa primero por un archivo temporal.** Un formulario multipart puede traer los campos (`id_paciente`, `tipo`...) _después_ del archivo, y la clave de almacenamiento y las validaciones dependen de ellos. Por eso el archivo se recibe en streaming a una carpeta temporal (`<tmp>/hc-uploads`, permisos 0600, nombre aleatorio) mientras se calcula el sha256, se cuenta el tamaño y se identifica el formato; recién con todos los campos validados se copia al almacenamiento definitivo y el temporal se borra siempre (en éxito y en error). En Render el disco temporal alcanza para `MAX_UPLOAD_MB` (25 MB por defecto) por subida.
- **Validación por contenido.** El formato se detecta con `file-type` sobre los primeros bytes (magic bytes) y se rechaza apenas llegan, sin esperar a terminar la subida. Se ignoran la extensión y el `Content-Type` del cliente: el `mime_type` guardado y la extensión de la clave salen de lo detectado (una imagen PNG subida como `foto.pdf` se guarda y se sirve como `image/png`). Un tipo no permitido devuelve 415 `TIPO_NO_PERMITIDO`; GIF, ejecutables, HTML o texto plano se rechazan. Esto no reemplaza a un antivirus (fuera de alcance, ver sección 12 del plan).
- **Límite de tamaño:** `MAX_UPLOAD_MB` (acepta decimales). Al superarlo se corta la transferencia, se responde 413 `ARCHIVO_DEMASIADO_GRANDE` con `Connection: close` y no queda nada en el almacenamiento ni en disco. Una subida con campos malos, vacía, con más de un archivo o que no es multipart devuelve 400.
- **Fichas antiguas solo imagen:** el esquema permite PDF en ambos tipos, pero el plan describe las fichas como imágenes escaneadas, así que `tipo = ficha_antigua` con un PDF devuelve 422 `TIPO_INCOMPATIBLE`, tanto al subir como al cambiar el tipo después.
- **Claves de objeto:** `estudios/<id_paciente>/<uuid>.<ext>` o `fichas-antiguas/<id_paciente>/<uuid>.<ext>` (uuid de `crypto.randomUUID`, que es lo que hace el paquete `uuid`, sin sumar otra dependencia). Un solo bucket con dos prefijos, como indica el plan: la variable `S3_BUCKET` es una sola. La clave nunca incluye nombres de pacientes y **nunca se devuelve por la API**.
- **Orden de la subida:** se descartan pedidos inválidos (paciente, consulta, formato) _antes_ de transferir al almacenamiento; luego se guarda el objeto; luego se inserta la fila y la auditoría en una transacción (revalidando paciente y consulta con bloqueo). Si la inserción falla se borra el objeto subido (hay test que simula la caída). Si el borrado también fallara, queda un objeto huérfano y se registra un error en el log con su clave, para limpiarlo con un script de mantenimiento.
- **Consulta asociada:** debe existir, ser del mismo paciente (regla 8) y **no estar anulada** (422 `CONSULTA_INVALIDA` / `CONSULTA_ANULADA`).
- **Paciente dado de baja:** no recibe archivos nuevos y, con el mismo criterio que en consultas, tampoco se editan, eliminan ni restauran sus archivos (409 `PACIENTE_INACTIVO`). Descargarlos sí se puede.
- **Descarga:** el `Content-Type` sale de la base. Además de `nosniff` y `Cache-Control: private, no-store`, se agrega `Content-Security-Policy: default-src 'none'; sandbox` (si alguien abre el archivo directamente, no puede ejecutar nada) y `Cross-Origin-Resource-Policy: same-site` (helmet pone `same-origin`, que impediría mostrar el archivo desde el frontend; el despliegue ya exige el mismo dominio registrable). `Content-Disposition: inline` lleva el nombre saneado, con `filename` ASCII y `filename*` UTF-8. Un archivo eliminado responde 404 `ARCHIVO_ELIMINADO`; si el objeto falta en el almacenamiento, 404 `ARCHIVO_NO_DISPONIBLE` (y se registra el error en el log).
- **Modo de descarga:** `DOWNLOAD_MODE=stream` (por defecto, el backend transmite) o `redirect` (302 a una URL firmada de `SIGNED_URL_TTL_SECONDS`, 60 por defecto, entre 10 y 3600). La URL firmada fija el tipo y el nombre de la respuesta. Con el driver local, que no firma URLs, `redirect` cae en transmisión. La auditoría `ver_archivo` se registra antes de entregar el archivo o la redirección.
- **Auditoría de archivos:** `archivo_subir` guarda paciente, tipo, formato y tamaño, **no** el nombre del archivo (puede llevar el nombre del paciente). `archivo_editar` guarda el antes y el después de tipo, fecha y consulta, pero de `descripcion` solo constancia de que cambió (puede ser texto clínico). Igual que en consultas, leer los metadatos de un archivo (`GET /archivos/:id`) registra `ver_archivo` con `vista: "metadatos"`, y la descarga con `vista: "contenido"`. El listado no se audita.
- **Metadatos de un archivo eliminado:** `GET /archivos/:id` los sigue devolviendo (para poder restaurarlo), con `eliminado: true`; `PATCH` responde 409 `ARCHIVO_ELIMINADO`.
- **Fechas del documento:** `fecha_documento` no puede ser futura (un día de margen por la zona horaria) ni anterior a 1900. El listado ordena por `subido_en` (por defecto, más reciente primero) o `fecha_documento`, y filtra por paciente, tipo, formato, rango de fecha del documento y eliminados.
- **SDK de S3:** `requestChecksumCalculation` y `responseChecksumValidation` en `WHEN_REQUIRED` y `forcePathStyle`. Las versiones recientes del SDK agregan checksums por defecto que Backblaze B2, MinIO viejos y otros compatibles rechazan; este ajuste evita ese problema conocido. El driver sube el archivo desde disco con tamaño conocido (`ContentLength`), sin multipart.
- **Pruebas de S3 sin Docker:** el plan pedía probar `s3` contra MinIO en Docker, que no está disponible. En su lugar los tests ejercitan el **SDK real de AWS** contra un servidor HTTP S3 simulado en proceso (PUT/GET/HEAD/DELETE, parámetros `response-*` de las URLs firmadas), con las mismas pruebas de contrato para el driver local y el S3 y la API completa sobre ambos. Si se definen `TEST_S3_ENDPOINT`, `TEST_S3_REGION`, `TEST_S3_BUCKET`, `TEST_S3_ACCESS_KEY_ID` y `TEST_S3_SECRET_ACCESS_KEY`, las mismas pruebas corren contra un bucket real **de pruebas** (nunca el de producción); recomendable hacerlo una vez con el proveedor elegido (Backblaze B2 o Cloudflare R2) antes de salir a producción. Lo que el simulado no cubre es el comportamiento propio de cada proveedor (TLS, firma de payload, límites).
- **Tests:** la suite completa tarda ahora más de 10 minutos contra Render. Para iterar, correr solo el archivo de la fase (`npx vitest run tests/archivos.test.ts`).

## Fase 6

- **Series mensuales calculadas sobre las tablas, no sobre las vistas `reporte_*`.** Las vistas del plan agrupan por mes pero no admiten un rango de fechas. Para respetar `desde`/`hasta` con precisión de día se consulta directamente `consulta`, `paciente` y `consulta_contenido` con las **mismas reglas que las vistas** (consultas no anuladas por fecha clínica, altas por `creado_en`, ediciones = versiones > 0), y hay un test que verifica que, sin filtros, los números coinciden con los de las vistas. Las vistas quedan disponibles en la base para consultas ad hoc.
- **Meses de Córdoba y rangos de días completos.** `desde` y `hasta` (inclusivos) son días calendario de `America/Argentina/Cordoba`; un mes se asigna según la hora de Córdoba (una consulta del 31/03 a las 22:00 cuenta como marzo aunque en UTC sea abril). Se aceptan fechas entre 1900 y 2100; un rango invertido es 400.
- **Los meses sin datos aparecen en cero** dentro del rango (pedido o, si no se pidió, del primer al último mes con datos), para que un gráfico no tenga huecos. Sin rango y sin datos la lista es vacía.
- **Forma de las respuestas:** las series y rankings devuelven `{ "data": [...] }`; el resumen devuelve un objeto plano. `mes` es el primer día del mes (`2024-03-01`).
- **`GET /reportes/resumen`:** `pacientes_total`, `pacientes_activos`, `consultas_total` (no anuladas), `consultas_del_mes`, `ediciones_del_mes` (versiones nuevas del mes calendario actual en hora de Córdoba), `archivos_total` (sin eliminados), `archivos_estudios` y `archivos_fichas_antiguas`. Se agregaron los totales de consultas y el desglose de archivos además de lo mínimo que pedía el plan.
- **`pacientes-por-obra-social`** cuenta solo pacientes **activos** (como el resumen de pacientes) e incluye una fila "Sin obra social" con `id_obra_social: null`, útil para un gráfico circular completo.
- **`consultas-por-paciente`**: ranking de pacientes por consultas no anuladas en el período, con `limit` entre 1 y 100 (10 por defecto); los empates se ordenan por nombre. Trae `ultima_consulta`.
- **CSV:** UTF-8 con BOM, líneas CRLF, y **separador `;` por defecto** (`CSV_SEPARADOR`, también admite `,`). Con la configuración regional de Argentina o España, Excel usa `;` como separador de listas, y con `,` abriría todo en una sola columna. Se neutralizan las celdas de texto que empiezan con `=`, `+`, `-`, `@`, tabulación o retorno de carro (también si hay espacios antes del signo) anteponiendo un apóstrofo; los números no se tocan, así que un valor negativo legítimo no se altera. Las celdas con separador, comillas o saltos de línea van entre comillas. El resumen en CSV sale como filas `indicador;valor`.
- **Exportar un reporte no se audita**, porque la lista oficial de acciones (sección 7.8) no incluye una acción para eso. Ojo: `consultas-por-paciente` exporta nombres de pacientes. Si se quiere dejar constancia de las exportaciones habría que agregar una acción (por ejemplo `reporte_exportar`) a la lista; queda como decisión pendiente para el desarrollador.
- **Auditoría (solo `admin`):** `GET /auditoria` lista del más reciente al más antiguo, con filtros `desde`, `hasta`, `id_usuario`, `accion`, `entidad` y `entidad_id` (todos combinables) y hasta 200 por página. `accion` y `entidad` solo admiten minúsculas, números y guion bajo. Cada ítem trae el usuario (`id`, `nombre_usuario`, `nombre_completo`, o `null` si el evento no tiene usuario, como un login fallido de un usuario inexistente), `ip` y `detalle`. `GET /auditoria/acciones` devuelve las acciones que existen en la tabla (se declara antes que `/:id`). La auditoría es de solo lectura: no hay rutas para crear, modificar ni borrar registros (el trigger de la base y los permisos de `hc_app` lo garantizan además).
- **`auditoria_ver` se registra al abrir un registro puntual** (`GET /auditoria/:id`) y **no** al listar, siguiendo la regla del plan de que las lecturas se registran al abrir un recurso puntual y no en cada listado. Hacerlo en cada listado llenaría la tabla de ruido (cada recarga de la pantalla agregaría una fila).
- **La lista de acciones es una constante única** (`ACCIONES_AUDITORIA`): el tipo de TypeScript sale de ahí, así que no se puede registrar una acción fuera de la lista. Un test recorre la API completa y comprueba que **cada una de las 25 acciones genera su registro**, que no se registra ninguna otra, y que en toda la tabla no aparece texto clínico (contenido de consultas, motivos, observaciones, descripciones, nombres de archivo) ni contraseñas (correctas o equivocadas).
- **Tests:** la suite completa ronda los 15 minutos contra Render. Para iterar conviene correr un archivo (por ejemplo `npx vitest run tests/reportes.test.ts`).

### Problemas encontrados y corregidos durante la fase

1. **El `build` no copiaba las migraciones `.sql` a `dist/`**, por lo que `migrar:prod` habría fallado en el servidor. Ahora `npm run build` las copia (`scripts/copiar-migraciones.mjs`); se verificó ejecutando el script compilado con `node` puro contra la base de Render.
2. **Los logs de errores de PostgreSQL podían incluir datos personales:** `pg` adjunta al error el campo `detail` (por ejemplo `Key (dni)=(30123456) already exists`), `where`, `hint` e `internalQuery`. El logger ahora serializa los errores con una lista de propiedades permitidas (tipo, mensaje, traza, código, restricción, tabla, columna) y descarta el resto (`tests/logger.test.ts`).
3. **`lib-postgres.sh` aceptaba una URL sin nombre de base** (`postgres://u:c@host`) tomando el host como base. Lo encontró el test del script; corregido.
4. **`.env.example` estaba incompleto** (faltaban `RATE_LIMIT_MAX` y las cinco `S3_*`). Se reescribió ordenado y se comprobó que cubre todas las variables que lee el código y que es válido para el validador de entorno.
5. **Cada corrida de `vitest` reinicia el esquema de la base de pruebas**, incluso la de archivos que no usan la base. Corriendo una segunda mientras la suite completa estaba en marcha, la primera falló de forma masiva (24 de 30 tests de consultas) sin que hubiera ningún defecto en el código. Quedó documentado en el README como regla: **nunca dos corridas de `vitest` a la vez contra la misma base**.
6. **Un test que se pasa del tiempo por lentitud de la red podía arrastrar al siguiente.** En una corrida completa (que tardó 24 minutos por la latencia hacia Render) un test excedió los 20 segundos y su petición, todavía en vuelo, chocó con el `TRUNCATE` del test siguiente (`deadlock detected`), de modo que fallaron 3 tests de consultas que pasan sin problema solos. No era un defecto de la API: sus transacciones toman siempre los bloqueos en el mismo orden (consulta y luego paciente; la baja de paciente solo bloquea al paciente), así que no hay ciclos entre peticiones. Se endureció la infraestructura de tests: el tiempo máximo por test pasó de 20 a 60 segundos y la limpieza entre tests reintenta ante un deadlock.

### Backups: decisiones

- **Formato `custom` comprimido** de `pg_dump` (permite restaurar tablas sueltas y verificar la copia con `pg_restore --list`), con **`--no-owner`**: en la base nueva los objetos quedan a nombre de `hc_migrator`. Los **permisos de `hc_app` sí se conservan** (la base destino necesita el rol, por eso se ejecuta antes `npm run crear-roles`; `restaurar.sh` lo comprueba y avisa).
- **La contraseña nunca viaja como argumento** de `pg_dump`/`psql` (se vería en la lista de procesos): la URL se descompone en variables `PG*` (`lib-postgres.sh`). SSL es obligatorio salvo en `localhost`, o lo que diga `sslmode` en la URL.
- **Verificaciones:** `backup.sh` descarta una copia que no se pueda leer y registra su SHA-256; `restaurar.sh` verifica ese SHA-256, **se niega a restaurar sobre una base que ya tiene tablas** y restaura todo o nada (`--single-transaction --exit-on-error`), mostrando la cantidad de filas por tabla.
- **Retención** por antigüedad del archivo (`BACKUP_RETENCION_DIAS`, 30 por defecto); solo borra archivos `historias-clinicas-*.dump` y su `.sha256`.
- **No se cifra la copia desde el script:** contiene datos clínicos y hashes de contraseñas, así que debe guardarse en un destino cifrado y privado (documentado). Los archivos del bucket **no** están incluidos: se respaldan con el versionado/replicación del proveedor.
- `hc_app` no sirve para el backup (no puede leer la tabla de migraciones): se usa `hc_migrator`.

### Riesgos y recomendaciones que no son parte del plan

- **Los límites de intentos por IP se llevan en la memoria de cada instancia:** con una sola instancia (lo previsto) funcionan; si algún día hubiera varias, cada una contaría por separado. El bloqueo de cuenta por contraseñas incorrectas, en cambio, vive en la base y sirve con cualquier cantidad de instancias.
- **Doble factor de autenticación:** fuera de alcance (sección 12 del plan) pero muy recomendable a futuro para un sistema de datos de salud.
- **Antivirus sobre los archivos subidos:** fuera de alcance; la validación por contenido frena los formatos no permitidos pero no detecta un PDF malicioso.
- **Actualizar dependencias** con regularidad (`npm audit` en cada despliegue) y rotar las contraseñas de `hc_app`/`hc_migrator` si alguna vez se exponen (se cambian volviendo a ejecutar `crear-roles` y actualizando las variables).
